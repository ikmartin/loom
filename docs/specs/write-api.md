# Write API

The write API is the HTTP form of the publisher's local commands, so that a browser can request record writes and the person's own acts on their files. It is served by the publisher (loom's `serve`), never by the viewer.

**[decided]** The commands it wraps are library functions with the same signatures, and a viewer detects it rather than assuming it.

## 1. Discovery

**[decided]** `GET /_api` returns `{"write_api": 1, "capabilities": [...], "token": "...", "quilt": "9f2c…", "pid": 4242, "stream": true, "connected": [...], "frames": "http://127.0.0.1:PORT", "viewer": "1794507956349", "stale": false, "home": "http://127.0.0.1:8790/"}` or 404, and 403 to a request a browser says came from another page (§3). `frames` is the frames origin an HTML file is shown from (§3), absent where none runs. `pid` is the server's own process, at which the home stops a server it found running (§7), since the `serve.json` in a quilt travels with a copy of it. `home` is the address of loom's home page (§7) while a home runs on this machine, absent otherwise, so a page whose server has stopped can send the person there. `viewer` is the version of the viewer the publisher serves (its `_app/version.json`): `loom serve` keeps the Python it started with, so it serves the machine's copy of the viewer version it started with rather than the vendored bundle, and a viewer vendored while it runs is not served beside code it was not built for. `stale` is true once the vendored viewer or loom's own code has changed since the publisher started. A viewer that finds `stale` says to restart `loom serve`; one whose own version is not `viewer` says to reload, and asks again whenever the stream reconnects. `stream` says `GET /_api/stream` is served: a `text/event-stream` with an event `manifest`, carrying nothing, each time a new manifest is published; an event `compiles` on opening and each time a compile starts, ends or is asked for, carrying one JSON object keyed by document path, each `{"state": "queued"|"compiling"|"idle", "again": bool, "last": null | {"result": "ok"|"errors"|"failed", "ended", "error", "at"}}`, where `errors` made a PDF though LaTeX reported errors, `failed` made none so the last good one stays, and `at` is the log's `l.N` line where TeX stopped; an event `connected` on opening and each time the list of connected agents changes, carrying that list as `connected` below; and a comment every fifteen seconds while idle. The token is what every write must carry (§3). `quilt` names the quilt the publisher serves, by a digest of where it lies and never the place itself, so a viewer can keep what it remembers per quilt: a folder copy served later on the same port is another quilt. A viewer that receives 404 or a version it does not accept shows no editing affordances. The capability list is what this publisher actually serves, so a viewer must read it rather than assume the table below: an endpoint absent from the list answers 404, and a viewer that hides the affordance is correct.

**[decided]** **Who is connected.** Each `loom mcp` process, the server an agent's app starts for one conversation, keeps a record of itself at `.loom/local/live/<pid>.json`, and `connected` is the records of the processes alive as `loom serve` last looked, at most a second ago, the oldest first, served where the stream is; no request waits on the records. A record is written at the server's first request of either kind (`initialize`, or any request of a client that sends none, such as `server/discover`), written again in place at each tool call, prompt or resource read and when a loom session is bound to it, and removed when the server is stopped by SIGINT, SIGTERM or SIGHUP or ends on its own. Each is one JSON object:

```json
{
  "format": 1,
  "pid": 4242,
  "ppid": 4200,
  "as": "Claude Code Agent",
  "client": {"name": "claude-code", "title": "Claude Code", "version": "2.1.312"},
  "protocol": "2026-07-28",
  "conversation": "5b6c0e2a-…",
  "entrypoint": "claude-desktop",
  "session": "s-2026-11-17-ab12",
  "loom": "0.1.0",
  "started": "2026-11-17T14:02:11Z",
  "last": {"kind": "tool", "name": "loom_annotate", "when": "2026-11-17T14:05:40Z"}
}
```

`pid` is the server's and `ppid` the process that started it, the agent's app; `as` the agent's name, under which it writes; `client` the app's own `name`, `title` and `version` as its first request gave them (a request's `_meta` `io.modelcontextprotocol/clientInfo`, or `initialize`'s `clientInfo`), null when it gave none; `protocol` the MCP version that request spoke. `conversation` is the app's id for the conversation (`CLAUDE_CODE_SESSION_ID` in the server's environment) and `entrypoint` how the app was started (`CLAUDE_CODE_ENTRYPOINT`, `claude-desktop` in the desktop app), each null where the app sets none. `session` is the loom session the server writes into, null until it has one (`docs/design/agents.md`). `last` is the latest call, `kind` one of `tool`, `prompt`, `resource` and `name` the tool, prompt or resource, null before the first. Times are the clock's, ISO 8601 UTC. Nothing counts the agents behind one record: an app's subagents share its connection and its name, so one record may stand for several, and a record is a conversation, not a person or a model at work. A viewer says "connected" of a record in the list and "active" of one whose `last.when` is recent; neither says the agent is working.

**[decided]** A record is one machine's: ignored by git, never read by a build, and checked when read, since it travels with a copied quilt and a process id is reused. The server holds an exclusive lock (`flock`) on its record's file for as long as it runs, and no command it runs inherits it. A reader that can take a shared lock on a record without waiting knows no process holds it, whatever its `pid` names now, and deletes it: so a server killed outright, a record copied with a quilt and a `pid` taken by another process all leave the list at the next look, which `loom serve` takes once a second and `loom mcp` takes when it starts. Only a regular file named for a `pid` in ASCII digits is opened, never through a link and never so that it waits (a FIFO), and `.loom/local/live/` only when it is a directory and not a link; anything else there is left alone, and no entry stops the look at the others. A record that does not parse, whose `pid` is not its file's name, or whose lock cannot be tried (a filesystem without locks) is left where it is and not listed. A server writes its own record over anything else standing at its name. A quilt synced live between two machines with an agent on each would see the other's record as unheld and delete it; that is outside what a record is for.

## 2. Endpoints

**[decided]** All requests and responses are JSON. Errors return `{"error": {"code": "...", "message": "...", "fields"?: {...}}}` with 4xx status, `fields` naming the reason for each field of a form it refused; the codes are the CLI's exit reasons. A request that names something that does not exist answers 404 with `no-such-` and what it named (`no-such-node`, `no-such-annotation`, `no-such-session`, `no-such-quote`, …), the same refusals the CLI exits 2 for; 400 is a malformed request or a write refused on its merits, 403 the CSRF gate (`refused`) or an author's act refused to an agent (`author-only`), 409 a conflict with the quilt's state. An annotation belongs to no session, so no annotation endpoint names one, and a `session` sent with one is ignored.

**[decided]** **A work added by hand** (plan 0.24.2) goes into loom's own bibliography, `.loom/library/bibliography.bib`, never a document's `.bib`, with `loom-added = {WHEN, WHO}`; the manifest's reference carries it as `added` (specs/manifest.md). `library-lookup`'s `found` is `{state, kind, label, value, entry, key, digest, duplicates, message}`: `state` is `found`, `missing` (the identifier names nothing: a DOI doi.org has no record of, an arXiv id arXiv does not have), `unreachable` (the service could not be asked, `message` saying why), `offline` (it needs the network, which neither `[library] online` nor `online` allows) or `cannot` (an ISBN, a MathSciNet number, or text that is no identifier, which loom does not look up); `entry` is the fields loom would write; `key` the key it would be filed as, unique; `digest` is `source` when an arXiv id lets loom fetch its LaTeX source, else `lookup`; `duplicates` names works already in the library with the same identifier or title and year. A DOI is asked of doi.org by content negotiation, an arXiv id of the arXiv API, a zbMATH number of zbMATH Open; a BibTeX entry is found from its own fields with no network. A request body over 96 MB answers `too-large` (413) before it is read.

**[decided]** **A library run is a job** (plan 0.24.1): a run can take minutes, a compile being allowed ten, so `library-update` answers with `{ok, result, job}` before it starts, and the publisher runs its jobs one at a time on a worker of its own, outside the lock its other writes take, rebuilding when each finishes. A job is `{id, kind: "library-update", works, steps: [{name, state, n, total, item}], state, who, online, redo, submitted, started?, finished?, error?, report?}`: `works` is the citekeys it acts on, empty for every work; each step is `waiting`, `running`, `done`, or `skipped` when it acted on nothing (offline, or nothing in it to do), with how far through the works it is and the one it is on; `state` is `queued`, `running`, `done` or `failed`, a failed run keeping its `error`; `report` is what `loom library update` prints, as its JSON envelope, whose `works` has one line per work saying what failed for it: `lookup_error` (the lookup could not be made), `discarded` (the paper fetched was not this work), `extract_error`, `map_error`. A viewer shows a work's failures from the last run on it while the publisher holds that run; nothing persists them. `online: true` is the person's allowance of the network for that run, as `--online` is, written nowhere; an agent cannot ask for it, since the endpoint refuses an agent. `GET /_api/jobs` answers `{jobs}`, the newest first, to this server's origin with the token, as `GET /_api/here` does. While a run acts on a work, `library-verify` and `library-discard` on that work's results answer `library-busy` (409), since the run writes its digest too. A publisher that runs no jobs answers `library-update` with `no-runner` (409). Jobs are held in memory, and a restarted publisher has none.

**[decided]** `GET /_api/events?session=ID&since=SEQ` answers `{session, from, seq, events}`: the events after `SEQ` in the transcript's page form (specs/manifest.md §10.1) and the last sequence number. It reads by an index of where each event starts, so a poll costs what is new; a `session` that is not an id's shape is refused.

**[decided]** `here` is the reader's place, which `loom here` reports to an agent. A tab posts it after a change of the focused item, the block at the top of its pane, the selection, the PDF page, the session or the block under review has settled, and again when it gains focus, so the tab touched last wins. `item` and `beside` are the focused pane's active item and the other pane's, in the viewer's item shape (`{kind, id, place?}`); `block` is `{src, key}`, the `data-src` and key of the block at the pane's top; `selection` is `{key, text}` in a document, `{file, text}` in a project file, or `{page, text?, rects}` on a PDF page, in points from the page's top left, the box tool's region included; a file item's `place` is its heading, `page=N` or anchor; `page` is the PDF page in view; `annotation` is the id of the annotation whose popup is open, which `loom here` names with a crop of its page when it is on one, as it does a region drawn on a page; `review` is `{key, cause}`, the block under review, the cause in the viewer's words: on `/review` in place of the workspace, and in a document beside Review's panel (`?review=`) alongside its item; on any other page, `route` is `elsewhere` and `path` is the viewer's. A place over 64,000 bytes, or with no `route`, is refused with `bad-field`. `GET /_api/here` answers `{place, when, age}`: the last place, the second it came and how many seconds ago, `place` null before any tab has reported. It requires the token and this server's origin, like a write, since where a person is reading and what they selected are theirs. Nothing writes it to disk, and a server's stop forgets it.


**[decided]** `compare` answers `{ok, left, right, pairs}`. `left` and `right` are `{item, kind, macros}`: the item as asked, `"document"`, `"landmark"` or `"node"`, and the manifest macro set its renderings are typeset with (`canon:<stem>` for a landmark, null for the default). Each pair is `{pair, base, left, right}`: the plain key; which side holds the base — `"left"`, `"right"`, `"both"` when the node changed on both sides since the version an agent document began from, or null when nothing orders them; and per side `{key, hash, fragment?}`, the node's key there, its `data-hash`, and a fragment path under the build directory with the changed words marked as Review marks them. A pair whose hashes agree is no difference and is left out, a display name changed alone included. A pair the quilt no longer has a live node for has no `fragment`, and the viewer keeps its whole-node marks. An item that is none of these is refused with `unknown-item`, 404. It is a read: the publisher does not rebuild after it. The answer is computed when asked, never at build, since the pairs two items can form grow with the square of the landmarks.

**[decided]** `session-purge` is **not** an endpoint and will not become one. Purging erases a session's directory and transcript for good, and the one place that should be reachable from is a terminal where the author typed the word.

**[decided]** `annotate` with `page` records an annotation on a page of a cited work (DR-209) through the same mapping `locate` previews — one function on the publisher, so what the viewer showed is what the log says. `locate` with `span` maps offsets into the page's committed text, which is what a `span=` locator in a URL carries. `locate` with `text` and no `page` maps the quote on the first page whose committed text holds it, which is what a `quote=` locator with no `page=` carries; it is refused with `not-found`, 404, when no page does.

**[decided]** `locate` maps a selection to an anchor **on the publisher**, never in the browser. The client's text layer is a third extraction of a page, after the committed page text and the word boxes; only the publisher holds the other two, and only the publisher can say what the page says. The client sends the selected string and never a decision about what the anchor is. Geometry-only anchors are legal and are never refused.

**[decided]** `undo: true` on `resolve` opens the annotation again (DR-174). It appends another event rather than removing one, so the record still says that it was resolved, when and by whom, and that it was reopened. A viewer offers it in place of the verb that fired, which is what lets those two act on a single click: a wrong one is one click back.

**[decided]** A change is kept or discarded where it is drawn, in its document or in Review, never resolved. Its id is what both endpoints take: `c-` and eight hex digits for an in-place edit, its content's hash, which stands while the change does, and a suggested edit's own id. Every write loom makes on the person's word goes into their look too, so a suggested edit kept is not listed back as an in-place edit of its words; a suggested edit whose key already reads as it taken is kept without writing. An agent withdraws its own open edit with `loom suggest --withdraw ID`; keeping and discarding are the author's.

## 3. Authorship

**[decided]** `author` defaults to the publisher's resolved author name; `as` declares an identity, and an agent names itself including `Agent` or `AI`. The author's verbs refuse a declared agent identity whichever surface it came through, here with 403 `author-only`. A write that names no author is taken for the author's own click in the viewer, which is why no page but the viewer may make one (below).

**[decided]** **Every write carries three checks.** They are CSRF protection and not a login: they keep other *pages* out, not other people.

1. **`X-Loom-Token`** must equal the token the server keeps outside the quilt, in a file only its owner can read in the machine's place (`loom/src/loom/machine.py`), which `GET /_api` serves and the viewer reads.
2. **The page it came from** must be this server's: `Origin`, when present, is this server's own, and `Sec-Fetch-Site`, when present, is `same-origin` (or `none`, the person typing the address).
3. **`Content-Type: application/json`** is required.

A browser blocks a cross-origin *response* and never the *request*, so any page the author happens to be reading could otherwise POST into their quilt and create, resolve or delete. A cross-site form post can set neither a custom header nor a JSON content type, which is what closes it. The socket still binds to loopback, which keeps other machines out; it never kept out the page the author was reading. A request failing any of the three answers 403 with `{"error": {"code": "refused", ...}}`.

**[decided]** **Every request names this server.** `loom serve` answers no request, a read included, whose `Host` is not `127.0.0.1:PORT` or `localhost:PORT` with its own port: it answers 403. A browser sends the name its page was loaded by, so a domain pointed at 127.0.0.1 (DNS rebinding) is same-origin with the server as the browser sees it and passes check 2, and would otherwise be given the token by `GET /_api` and every file under `/_files/`, `/build/` and `/digests/storage/`, which ask for no token. A viewer reached through a tunnel must keep the server's port.

**[decided]** **No page but the viewer runs in the viewer's origin.** The token keeps other sites out, but `/build/` and `/digests/storage/` are served from the viewer's own origin: `/build/` serves what loom derives (`.loom/cache/site/`, and the compile folders of `.loom/cache/tex/` under `/build/tex/`), which an agent running as the person can still write, and `/digests/storage/` serves the store (`.loom/library/storage/`), which holds fetched sources nobody at loom wrote. So everything but the viewer's bundle, which is those files and every JSON answer, is served with `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`. A page there, HTML or SVG, runs no script and has an opaque origin: it cannot read `/_api`, and a POST it made would carry `Origin: null`, which check 2 refuses. `GET /_api` applies check 2 too and answers 403 `refused` when it fails, so the token goes only to the viewer's own origin. The viewer reads these files with `fetch`, `<img>` and PDF.js, which a response's sandbox does not touch, and a PDF opened in a tab of its own is shown by the browser's viewer as before. A project file the viewer shows is served the same way at `/_files/PATH` (manifest §1, `files`), and nothing hidden is.

**[decided]** **A Markdown file's body is drawn in the viewer's own page**, so a publisher writes the HTML it holds through an allowlist first (specs/dialect.md §1), and nothing from it runs as the viewer: not a script, a handler or a `javascript:` address. A frame in it loads only an `https:` address, which is never this origin, since `loom serve` answers on `http:`. The body is confined under `/build/` as every file there is, which does not touch the viewer's read of it, and the viewer's own page carries no policy that would stop the frame.

**Open.** The allowlist is the publisher's, and a viewer inserts what it reads. An agent running as the person can still write `.loom/cache/site/`, though it is no place of the agent's, so a body or a manifest it edits there directly reaches the page unfiltered and can read the token; this was reproduced on 2026-11-04 against a real `loom serve`, and predates HTML in Markdown files. See the [invariant](../design/invariants.md#a-page-the-quilt-holds-never-runs-as-the-viewer).

**[decided]** **An HTML file runs on the frames origin** (plan 0.22.7). `loom serve` answers the project's shown files a second time on a loopback port of their own, which `GET /_api` names as `frames`, so an HTML file the viewer frames runs as a page of its own origin: its scripts run and embedded players (a video) play. That origin serves GET and HEAD for shown files and nothing else — no `/_api`, no bundle, no build output, no store — answers only a request addressed to its own host and port, and sends no CORS headers; check 2 refuses it, so a page there can never read the token or write. **What a page there may rely on:** it reads the project's other shown files by their paths; `GET /.loom/files.json` answers `{"files": [PATH…]}`, every shown file sorted, at an address no shown file can have since `.loom` is never shown; and its `quilt:`, `cited:` and `app:` links go through the bridge below. It has no way to write. Its browser storage lasts only until `loom serve` restarts, since the origin's port is chosen anew each time. Every answer from that origin carries `Content-Security-Policy: connect-src 'self' data: blob:`, so a page's scripts connect (`fetch`, `XMLHttpRequest`, a WebSocket, an event stream, a beacon) to that origin alone, and a player on the page whose script fetches its stream from another host does not play. The policy limits nothing else: a frame, an image, a video or a script from another host still loads, which embedded players need, and such an address can carry what the page read, so an HTML file in a quilt is still trusted as any program the person runs is. Into each HTML page it adds a small script, the bridge, that posts to the viewer's origin alone: a click on a `quilt:`, `cited:` or `app:` link, which the viewer follows as its own; the words selected, which the viewer reports to `here`; and a move to a new anchor. The viewer frames the page with `sandbox` keeping its origin but granting no top navigation, and drops every message not from that frame and that origin. Where no frames origin runs, a viewer shows the page from `/_files/` with no script.

**[decided]** **`open` never runs code.** It opens an application by a plain name (letters, digits, spaces, `.`, `-`, `_`; `open -a` on macOS, `gtk-launch` on Linux) or a shown file whose suffix is a document's — a notebook, a spreadsheet, an office document, an Anki package, audio or video, a book — and refuses a file with an executable bit, a hidden file, and any other suffix (`not-openable`, `no-such-file`, 400 and 404). An agent can write a file and a link to it into the quilt; it cannot make the person's click execute it.

## 4. No model behaviour, and no bridge

**[decided]** A publisher calls no model and starts no agent (plan 0.20.1). A session's inbox is its transcript: agents write it with `loom session say`, and the viewer reads it through `GET /_api/events` and posts nothing into it, since a conversation with an agent happens in the agent's own app. An earlier draft routed a reply through "the bridge": a component that watched threads and invoked the runner. The runner was declined as WQ-15, so the bridge had nothing left to invoke; the viewer's message composer and loom's launching of an agent for a turn (DR-195, DR-203, DR-273-ikmartin, DR-278-ikmartin) were retired in plan 0.20.1. Loom holds no credentials and calls no model.

**[decided]** The direction is the other way round, and it already works: an agent **pulls**. It reads open annotations with `loom status` and `loom ai annotations`, and answers with `loom annotate --reply`. That needs no server, no credentials held by loom, and no tracking of vendor flags that churn. A person writing in the viewer and an agent answering in its own session are the same log seen from two ends, which is what the log was for.

### Mathematical decisions during incorporation (DR-316-luisa)


`adopt-preview` returns, as `result.review`, a review preview `{token, reviewer, items}` for the selected agent document's changes. Each mathematical item has `{key, name, reason, local, proposed, unavailable}`; local and proposed hold `{path, macros}` for isolated renderings, local may be null for new blocks, and unavailable explains why acceptance is disabled. Items include unchanged dependent proofs and exclude structural sections and prose. Preview preparation changes no acceptance records or author source.

`adopt-finish` optionally takes `review_token` and `accept: string[]` with the effective `reviewer`. Omitting accept accepts nothing. Tokens bind the exact source, proposed patch and reviewer; foreign keys, repeated keys, changed source and stale selections are refused before application. After incorporation the selected blocks' fingerprints are checked again, applicable masters must compile and stale mathematical support must be included in the acceptance batch. The result adds `accepted` and `pending` lists. All unselected preview items remain explicitly pending. If incorporation succeeded but acceptance validation failed, the success result includes `acceptance_error` and pending mathematics; the UI reports both outcomes without suggesting that source application failed. The final server rebuild publishes the resulting review states. Prose has no acceptance action.

## Section drafts and responsive choices (DR-323-luisa)

`adopt-decision` is a metadata-only publication. The body carries the displayed contribution fingerprint and saved choice revision (initially zero); a stale revision returns 409 rather than overwriting another tab. Its returned result has `keys`, `kept`, `document`, `preamble`, `revision` and `fingerprint`. The fingerprint digests the comparison's own inputs: the copy and its baseline, the files and preamble of the document it was made from, the quilt's id prefix, the history's entries for that copy, and the context's inputs. A save to any other file leaves it, and with it a saved choice and a preview, as they were; taking the contribution in decides again under the door's lock (`docs/design/writes.md`). Every successful selection increments the revision; the manifest publishes the same authoritative row without rendering or compiling. The viewer applies that row immediately and ignores older rows for the same reviewer and fingerprint. A manifest poll containing only changed adoption choices preserves the loaded rendering.

`document` selects prose and ordering; `preamble` separately selects macros and packages, and is false by default. Choices whose base/current/proposed inputs still agree survive unrelated source changes; `invalidated` names choices needing inspection again. Preview tokens bind source, proposal, context, reviewer and choices. Selection does not accept mathematics. A copy's review shows accumulated outstanding edits, not just the latest agent message; leaving a change out keeps it available.

Closing and reopening are author actions. Close with outstanding proposals first returns `confirmation_required`, `unapplied` and a message without closing; resend `confirmed: true` to preserve the snapshot and release the scope. Closed source remains on disk but is excluded from the live scan. Reopen refuses a changed retained file, missing source, overlapping scope or occupied identities. The saved rendering and annotations remain readable under the original document path.

## 6. The library's intake

One intake takes in everything a person adds to the library: files dropped anywhere on the viewer, a pasted text, and `loom library add` on the command line, which goes through the same function (`loom/src/loom/refs/intake.py`) and reports the same rows. It replaces `library-upload`, `library-file` and `library-add`, which stay until the viewer's Add dialog is replaced. Every endpoint here is the author's, refused to a declared agent with `author-only` (403).

**A drop** waits in `.loom/local/incoming/<id>/`, one directory per item, which stays on one machine (`.loom/.gitignore`) and is never under `.loom/cache/`, which loom may delete. `<id>` is the file's sha256, or for a pasted text `t-` and the first 16 hex digits of the text's own. While it waits it holds the file, as `document.pdf` whatever it was dropped as, so two receives of the same bytes keep one file; `arrived.json` (`{name, size, when, not}`, `name` the name it was dropped under and read under, `not` the works it is known not to be); and, once a question is asked, `question.json`. When it is taken the file goes into the store, and `act.json` records what the act wrote, which is what `library-undo` reads. **A drop lets go of its file only once the act is recorded, and only while these very bytes, by hash, stand in the store at a place an entry names**; every act moves a document by linking its new place, recording itself, then removing the old link, so at no instant is the only copy somewhere the records call disposable. A file beside a record that says its bytes were taken in, whose bytes the store does not hold, as an act stopped midway leaves it, waits and is taken like any other. The same bytes received again while an add stands are let go, the add recording that they were (`received`), and that add's undo gives them back to wait.

| endpoint | request | answer | refused with |
|---|---|---|---|
| `library-receive` | the file's bytes, `Content-Type: application/octet-stream`, its name in the query (`?name=`), with the token and from the viewer's origin as every write | `{incoming, name, size}`; writes only `.loom/local/incoming/`, and the publisher does not rebuild | `not-a-pdf` (400) for bytes that do not open as a PDF, an empty body among them; `cut-short` (400) for a body that ended early; `no-space` (507) when the disk cannot hold it with 256 MB to spare; `missing-field` (400) with no name; `length-required` (411) with no `Content-Length`; `refused` (403) as §3; nothing is kept from a refused upload |
| `library-take` | `{items: [ITEM…], fetch?, author?}`, an ITEM `{incoming, for?}`, a received file and the work it was dropped on, or `{text}`, identifiers one a line or BibTeX entries | `{rows: [ROW…]}`, a row per file, per pasted line and per BibTeX entry, each with `item`, its index in `items`; `fetch` queues a run that fetches each work added; works an agent suggests will come in here as an item of their own (not built yet) | `network-unasked` (409) while the quilt has not said whether loom may use the network; `no-such-incoming` (404) for a drop not received; `no-such-work` (404) for a `for` that names none; `bad-field`, `missing-field` (400) |
| `library-answer` | `{question, same, author?}`, `same` a candidate's citekey, or null for a work of its own | `{row}` | `no-such-question` (404); `not-a-candidate` (400); `library-busy` (409) |
| `library-undo` | `{id, act?, author?}`, `act` the act the person means, a row's `act` | `{result, row?}` | `no-such-intake` (404); `not-last` (409) when `act` is undone already or another came after it; `not-new` (409) once the work has results, citations or annotations; `changed` (409) when the bibliography or the store holds what the act did not leave there, the refusal naming it; `untrusted` (409) for a record loom could not have written; `library-busy` (409) |
| `library-unfile` | `{citekey, author?}` | `{incoming, act, row}`, the drop the document waits in again and the act that took it off | `no-such-work` (404); `no-document` (409) for a work holding no PDF; `has-results` (409) for one whose results were read off it; `own-document` (409) for a work that came in with this very PDF, which an undo or a delete takes out whole; `already-waiting` (409) when the same file waits in a drop already; `library-busy` (409) |

**A row** is `{id, item, name, state, …}`, in exactly one of four states:

- `added`: the work is in the library, with `citekey`, `title`, `authors` and `year`; `under` names the existing work it was filed under (absent for a new work) and `sibling` the version entry it was filed as beside that work's first document; `pages` is `read`, `none` (no page text, `why` saying why: a scan has no text layer, and opens with nothing to search or quote) or `reading`, with the `job` that reads them; `act` names the act that added it. `library-undo` with its `id` and `act` takes it out again.
- `here`: these very bytes are held, or for a pasted text the library has the same work (one stating its identifier, or, neither stating one, its authors, title and year): `citekey` and `why`. Nothing is written; a waiting drop of it goes, and one an earlier act stands on lets its file go under an act of its own, which `library-undo` gives back.
- `question`: one question, "is this one of these works?": `question` (its id), `document` (`{title, byline, identifiers}`, what the PDF shows of itself) and `candidates` (`[{citekey, title, authors, year, how}]`, `how` the evidence in words). Nothing is written but the waiting file. `library-answer` settles it.
- `cannot`: `code` and `why`: `not-a-pdf`, `unreadable`, `not-recognised` (a text that names no work), `offline` (an identifier that needs the network, which the quilt has off), `missing` (it names nothing), `unreachable` (the service could not be asked), `no-service` (an ISBN or a MathSciNet number, which loom does not look up). Nothing is written.

The manifest's `arriving`, present only while something waits, lists the waiting drops as rows: each in state `question`, or `received` for a file received and not yet taken, which is never the answer to a take.

**Nothing is filed under an existing work unless the person says it is that work**: `same` in an answer, `--for` on the command line, or `for` on an item when the PDF shows nothing against it; a PDF that shows it is another work, or bytes another work holds, make a question or `here`. A strong match only chooses the question. The candidates are the works the PDF names by its own identifier (arXiv's stamp in its margin, or an identifier set apart at the head or foot of page one, beside no prose and the one of its kind there, with the work's title on that page; a DOI it prints comes before a preprint's arXiv id it prints beside it), by its whole title with the work's first author leading its byline, or by a reference manager's file name; and the works whose identifier, or title and year, the entry the PDF makes of itself shares, so a work whose entry names no author is still offered when the PDF's own title is its title. A work in the drop's `not` is never a candidate. An identifier on a line that begins by naming what the document answers ("Erratum to", "Comment on", "Reply to" and the like, never "Review of" or "Supplement to", which begin journals' names) is the answered work's, which it cites. A file given twice is `here` the second time, in one take or two. A work of its own never states an identifier another work in the library states: one identifier names one work, and a PDF said not to be that work only cited it.

**Only the same bytes are already here.** Loom discards nothing a person gives it but bytes it holds already, or what the person discards. A PDF that only looks like a document the library has, the same title, byline and page count or the work's own identifier read off it, is another document: on the person's word it goes beside the work's first document as a version (`<key>-v2`), and without it the intake asks its one question.

**The network is asked about once per quilt.** While `[library] online` is unset, `library-take` refuses with `network-unasked` before it reads anything, and the received files wait; the viewer asks the person once and saves the answer with `settings-save` (`library.online`). A quilt whose `config.toml` says `online = false` has answered. With the network allowed, the identifier a PDF states as its own is looked up and kept when the PDF carries the title found; a pasted identifier is looked up. `loom library add` reads an unset quilt as offline and says so; `--online` allows one run. **No lock is held while the network is asked**: each lookup of an item is made first, and the item is then decided again under the library's lock on what is true then, with the answers already heard; `library-take` and `library-answer` run outside the publication's lock, so a slow or silent service holds up no other write, no receive and no rebuild, and a service that never answers is `unreachable`. A command-line add of bytes that wait in a drop takes that drop, so its record stays with its file, and its undo leaves the file waiting there again.

**Undo and unfile.** `library-undo` reverses the last act on a drop: an add (a new work, or a document filed under one, with every record the act wrote; the drop goes too, unless an earlier act on it stands, when its file waits again as `received`), an unfile (the document goes back under its work), a drop let go as already held (it waits again), or a drop still waiting (it is discarded). A work added is the act's to undo while it has no results, no citations and no annotations; a document filed under a work the person had, while nothing has been read off it. **An undo touches only what its act left, each part checked by its content, and otherwise refuses (`changed`) with nothing touched, naming what is in the way.** The bibliography goes back byte for byte while it holds what the act left; otherwise each entry the act wrote is found by the exact text it wrote and taken out, so an entry the person has since edited or renamed refuses the undo rather than leave its document's place empty. An add is refused too when its place in the store holds anything but the document it added, when another entry names that place, and when a work it made, a pasted one included, has a document or a version filed under it since. An unfile's entry goes back at its place while the bibliography holds what the unfile left, else at the end; it is refused when its work holds a document again, when the work's entry is gone or names another place, and when another entry has taken its version's key or names its place. The ledger's records go back only where they still hold what the act left. An undo writes the records before the store lets go of a document, and its drop's record last, so an entry never names a place emptied under it and an undo stopped midway leaves its act to be undone again or refused in a sentence. The record of an act is checked before it is acted on, since a drop travels with a quilt copied as a folder. `library-unfile` takes a work's stored PDF off it, with its page text and the version entry made for it; the work and its entry stay. A work that came in with that very PDF, added by hand or adopted by gathering, is not unfiled, since it would be an entry for nothing: an undo or a delete takes it out whole. **No document is written into a place in the store that holds other bytes or that another entry names**: a work of its own or a version goes to `file/<hash>-2` and on, and its identity follows its place; a place holding these very bytes and named by no entry, as an add that stopped midway leaves it, is this document's. The PDF waits again in `.loom/local/incoming/<sha>/`, with that work in `not`. The person's own file, wherever it was dropped from, is never touched.

**One lock for the library.** Each item of a take is decided and written under the library's lock, against the bibliography as it is then and not the caller's scan, so a work deleted meanwhile is `no-such-work` and a pasted text is compared with the entries there now, and so are an answer, an undo, an unfile, a delete and gathering's adoption of what the store holds, each from its checks to its last write: two adds of the same bytes at once add them once, two versions filed at once take two keys, a second click on discard finds the drop gone, and gathering never adopts a document an add has stored and not yet named. A receive waits on no lock: its bytes are kept before anything that can wait or time out, placed whenever no file waits in the drop, and a copy it places beside an act that took these bytes in goes the way every drop's file goes, by the rule above. A library run's fetch writes a PDF it downloaded under the library's lock and never over a document, so one the person filed on that work during the download stays; a take for a work a run is acting on is refused (`library-busy`), as every library write on that work is. The bibliography is read and written without translating its line endings, so a file kept with CRLF stays CRLF and nothing an act did not write changes.

**`library-receive` is the one request that is not JSON.** Its bytes are streamed to disk as they arrive, at any size; `application/octet-stream` is not a type a page of another site may send without asking first, so it keeps out what check 3 of §3 keeps out, and the token and the page it came from are checked as for every write.

## 7. The home server

**[decided]** `loom app` serves loom's home page, which opens, creates and lists a person's quilts, on port 8790, or on a free port when that one is held; it records its port, pid and address in `app/home.json` in loom's folder for the machine, which is trusted only while the home there answers `GET /_api` with that pid. One home runs on a machine: it holds `app/home.lock` while it runs, and a second `loom app` finds the first, says its address and exits. It holds no quilt. It serves the viewer it started with, as a quilt's server does, and none of a quilt's files: `/build/`, `/digests/storage/` and `/_files/` answer 404. Its guards are §3's: a request must name its own host and port, `GET /_api` and every write are refused to a page a browser says came from elsewhere, and every write carries the token and is JSON.

**[decided]** `GET /_api` returns `{"home": true, "pid": 4242, "token": "...", "capabilities": [...], "viewer": "...", "stale": false}`; `home` is how a viewer knows to draw the home page and not a quilt.

**[decided]** The home keeps a list of quilts, `app/quilts.json` in loom's folder for the machine, each known by a digest of where it lies (§1's `quilt`) and keeping one port for good: a quilt first seen already served keeps that port, a new one takes the first port from 8800 that no quilt was ever given and no other program answers on, at 127.0.0.1 or `::1`, and a port is never given to a second quilt, since a viewer keeps its preferences per port and its layout per port and quilt name. A list that is there and cannot be read is kept as it is: the home lists no quilt, says `list: "unreadable"`, and every endpoint that would read or change the list answers `list-unreadable` (409) until it can be read. `loom serve` with no `--port` takes the port its quilt keeps. Each quilt the person opens is served by the unchanged `loom serve --port PORT --quilt ROOT`, in a process of its own, which the home finds again by its port answering `/_api` with its quilt's id, and stops at the `pid` it gives there. It starts again a server that died unasked after 2, 10 and 60 s, and then shows it as failed; one that refused to start (exit 2) is not started again; one quilt the home cannot serve is that quilt's failure, and the rest stay served. It restarts a server whose `/_api` says `stale` on the same port once loom's code has been still for 30 s, and then starts itself again once no quilt is being made. When it starts, it serves every quilt the person left open.

The paper's main file is the one an arXiv source's `00README.json` names as its top level, else the one `.tex` holding `\documentclass` and `\begin{document}` outside comments. The quilt is made with no tutorial `README.md` and opens on the paper (`[quilt] home`); the paper comes in through the import's one act with every theorem-like `\begin` and `\end` put on its own line in the drafted document, and the paper as received is kept as it came. A paper that does not typeset still comes in (`typeset: false`, `untypeset` the first error); a drafted document that does not typeset as the paper did comes in too, unchecked, with `differs: true`. A `.tex` or an archive dropped on an open quilt is the library's (§6); the home's drop is how a person's own paper makes a new quilt.
