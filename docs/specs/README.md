# The build directory loom writes and its viewer reads

This directory specifies what loom publishes into `.loom/cache/site/`, which the server answers at `/build/` with each document's compile folder (`.loom/cache/tex/`) under it at `/build/tex/`, and what its viewer reads there and asks of it: the HTML dialect of fragments, the manifest, the diagnostic codes, the write API, and what loom reads from an author's LaTeX. Loom and its viewer are one tool (P11): the viewer is built from `viewer/` and vendored inside loom, so the two change together and nothing between them negotiates a version. The interface files (dialect, manifest, diagnostics, fixture, write API) mark normative statements **[decided]**, a convention kept from the old design book; `source-contract.md` and `library-views.md` state their rules plainly, and `nodes.md` marks **[decided]** a rule the author settled. What the specs describe is what the code does: where one disagrees with the code, one of them is wrong.

## Files

- `dialect.md` : the semantic HTML dialect of fragments.
- `manifest.md` : the schema of `manifest.json`.
- `diagnostics.md` : diagnostic codes, reserved and loom's own.
- `source-contract.md` : what loom reads from an author's LaTeX: nodes, ids, proofs, edges, directives.
- `fixture.md` : the fixture and how it is used.
- `write-api.md` : the write API, the HTTP form of loom's local commands that the viewer calls.
- `reserved.md` : the names work in progress will add to all of the above, none of them built yet.
- `nodes.md` : the library's nodes, one file each: ids, the header, the body, references, macros and proofs, the edges a file states, the checks, the index and the tag log. The file, its checks, the index, the tag log and the references and macros nodes made from the works a quilt holds are built; nothing makes a statement or a proof from a work yet.
- `library-views.md` : what the viewer's four views ask of the publisher for the rebuilt library, read by read and write by write. Not built yet; when it is, the library leaves the manifest, and the publisher's obligation 3 and the viewer's 1 and 2 below take in its reads and the stream's `library` event.
- `names.md` : the names a person reads in the viewer, one for each thing, frozen for v0.1.
- `evidence.md` : the evidence log and the asks log under `.loom/records/`: what someone did to a text, by its hash, and what a person and an agent asked of each other.
- `tools/validate-dialect.py` : the fragment validator both codebases vendor; `tools/refresh-fixture.sh` : regenerates `fixture/` and both vendored snapshots.

## Changing what crosses

**[decided]** A change to what loom writes or what the viewer reads changes both sides and these files in one commit, and regenerates the fixture (C3, C5). No version is written into the manifest or checked by the viewer: the viewer reading a build directory is the one vendored in the loom that wrote it, and `scripts/checks/bundle.py` and `loom doctor` say when that vendored viewer is older than `viewer/`'s sources.

## Obligations of loom as publisher

1. Write fragments conforming to `dialect.md` and a manifest conforming to `manifest.md`, every section of it.
2. Publish atomically: fragments first, manifest last, by rename.
3. Never depend on the viewer for anything: no callbacks, and no notification beyond a stream that says a new manifest exists and how each document's compile stands (`GET /_api/stream`, specs/write-api.md), which a viewer may ignore; a build directory served as static files is read whole.
4. Carry every diagnostic it knows about into the manifest, using reserved codes where they apply.
5. Regenerate the whole build directory from source on demand; nothing in it is durable.

## Obligations of the viewer

1. Treat the manifest as the only index; never derive structure from fragment contents beyond what the dialect marks up.
2. React to changes only by detecting that `manifest.json` changed; never assume kinds of change.
3. Render unknown diagnostic codes, unknown state labels, and unknown taxa generically, never fail on them.
4. Write only through the write API, which loom serves.

## The fixture

`fixture/` (beside these files) is the build directory of the synthetic quilt, generated by loom with TeX and regenerated when what crosses changes; each codebase vendors a snapshot, so the viewer's suites run without TeX. See `fixture.md`.

`fixture/views/` holds, for each read and write of Review's and the Web's families (`evidence.md` §6 to §8), a sample request and the answer loom gives it, one JSON file each: `{endpoint, request, answer}`, a refusal's answer with its `status`. `loom/scripts/gen_views.py` writes them, as the `views` step of `scripts/regen`, on a copy of the synthetic quilt whose last build is this fixture's manifest, under the fixture's fixed time and without TeX. The step runs after the fixture's refresh, which makes `fixture/` again from nothing, and the two vendored snapshots do not carry the samples: the viewer's tests read them here. The viewer's sample data for these reads is these files, so the two sides cannot drift.
