# Writing a person's file

Loom writes a person's file only when the person asks it to (P7): keeping a suggested edit, undoing that Keep, discarding a change, restoring a version, putting back what a discard set aside, ticking a box, saving Settings. This page is the design of the one path all of those writes take, called the door: one lock shared by every loom process, a journal written before any file, the bytes of every file it replaces kept exactly, and recovery from a write that a crash cut short. It is written to be read on its own; what it builds on is named where it is used.

## Why there is one door

Each of those acts used to read the file, decide and write by itself. The v0.1 study (`docs/reports/v0.1-study/raw/safety.md`, `raw/spike-door.md`) measured what that did to a person's text on copies of real quilts:

- A save made by the person's editor while Keep ran was lost, because Keep wrote the file from the text it had scanned before.
- Two Keeps at once, from the viewer and an agent's shell, wrote one edit twice, or lost one edit while recording it kept.
- A crash between writing a file and recording the write left an edit in the file and still open, and the next Keep wrote it again.
- Keep and restore rewrote a file in the scan's reading, so Windows line endings became Unix ones; Discard in such a file spliced at offsets of one reading into the other and corrupted it.
- Restore overwrote a file that its document no longer reached without keeping it anywhere; Settings kept nothing of `config.toml` first and left it readable by its owner alone.
- Put-back wrote wherever the request's path pointed, outside the quilt included.

Each of these is the same fault: no lock across processes, no record before the write, and no exact copy of what was replaced. The door is the one place those three things are done (P4), so that every act gets them and none can forget one.

The door does not make loom read text better. Faults in which loom misjudges what someone else wrote (whether text the person typed is already the suggested edit, which block a key named by place means) are placement's, not the door's, and are handled where edits are placed (`records/edits.py`, "Where an edit goes" below).

## What counts as a person's file

Any file in the quilt outside `.loom/` and outside the history directory (`[quilt] history`). Loom's own records (logs, looks, the ledger) and what it derives are written by their own modules under their own locks, and are not person's files. `config.toml` is a person's file: they edit it, and Settings writes it.

## The act

A write is an act: `with writes.act(quilt, kind, actor) as w:`. Inside the block the caller reads the files it will write, decides, and stages what it will write; when the block ends without an exception the door writes it. Everything below happens while the act holds the lock.

1. **Recovery.** Whatever a crash left unsettled is settled first (below), so every decision that follows sees a quilt in which each earlier act happened whole or not at all.
2. **Decisions again.** The caller decides again what to do, by record and by the bytes now: whether a suggested edit is still open, whether loom has already written it (the journal says), whether an in-place change still waits, what a box says, what the config holds. A list made before the lock, and the scan a request was answered from, are advisory: another act may have run since.
3. **Reading.** `w.read(rel)` is the file's bytes now; the last read of a file before it is staged is what the act replaces. `w.text(rel)` is those bytes as UTF-8 with their own line endings, and refuses a file that is not UTF-8 (`not-utf8`). An act that writes into a file's text (Keep, Discard, a tick, Settings) reads it as text; an act that writes stored bytes whole (restore, put-back) reads bytes and never decodes them.
4. **Plans that are not stale.** A tick, Settings and Discard plan from the bytes they have just read, so there is nothing stale to check. Keep plans from a scan, which costs too much to repeat on every act, so `w.reads_as(rel, planned)` checks that the file, read now as the scan reads it (UTF-8, with CRLF and CR read as LF), is the text the plan came from (`w.expect` refuses outright when it is not). The offsets a plan holds are offsets in that reading, so this equality is exactly what makes them valid in the bytes on disk; a hash of the raw bytes would refuse a change of line endings alone and protect nothing more. When the check fails, Keep scans once more under the lock and plans again; if the file moves again it refuses with `changed`.
5. **Versions.** A version History shows ("Before keeping a suggested edit", "Before restoring …") is stamped inside the act, from the scan just confirmed, so two acts never stamp over each other and the version holds the text the act replaces. Stamping takes a moment in which the person's editor may save, so Keep checks its plan once more after the stamp, and splices into exactly the bytes that check read (`w.text(rel, again=False)`); a save after that is caught at the last read before the rename (step 7).
6. **Staging.** `w.replace(rel, data, splices)` stages the new bytes. Text goes in through `writes.splice`: each change is placed at offsets of the scan's reading, mapped onto the file's own text, and inserted text takes the file's own line ending, so every byte outside the change is kept. `w.log(log, line)` stages a record line that belongs to the act and is written with it; the log must be one of loom's own three (the edits', the annotations' and the ledger), or the act is refused with `outside-quilt`. `w.then(fn)` stages a follow-up: work that needs the files as written (a rescan, the person's look, carrying annotations onto changed words). `w.confirm(rel, data)` names a file the act leaves as it is because it holds `data`, what the act would write there, already: the act reads it under the lock and again just before it is journalled, and refuses (`changed`) when it holds anything else, never taking the caller's word; the file goes into `begin`'s files with its before and after one digest and is never written, and a file is staged by an act or left by it, never both (`staged`). Recovery writes nothing for such a file and judges the act by the files it writes, so a line that says so of a file, forged or not, has recovery write nothing there; it finishes the act only while each such file still holds what the line says the act found, and leaves it otherwise, as an act whose file changed since. What it is for is below: a left act of the same kind that names the file counts it as written again.
7. **Commit.**
   - Every before and every after is stored in the history's `texts/`, named by the sha256 of its bytes (`<hex>.md` when the bytes are UTF-8, `<hex>.bin` otherwise; the names `records.snapshots.write_raw` gives), but for the after of a file the act makes that is not UTF-8 or is over 1 MB, a figure or a saved PDF: that is journalled by its digest alone, since undoing it needs only to know it (recovery removes it while it holds those bytes), and its bytes in a store that is committed would be kept for nothing. So the store holds the before of every file an act replaced or removed and the after of every text it wrote. The texts of a file only this machine reads go beside the journal instead, in `.loom/local/texts/` (`writes.this_machine`), and recovery reads both stores. That file is an agent app's MCP file (`ai.clients.PROJECT_FILES`), which names this machine's loom and the quilt's absolute path. In the committed store it would carry one machine's paths to every co-author, and a quilt made twice, as the generated quilts are, would differ with where and by whom it was made.
   - A `begin` line naming the act, each file's before and after, its splices and its record lines is appended to the journal and flushed to the disk (`F_FULLFSYNC` where macOS offers it) **before any file is touched**.
   - Each file is written whole or not at all: its folder opened once, the real path a part at a time without following a link, and made only for a file the act makes, so the folder of a file it replaces, gone since, is refused (`changed`) rather than made again; a temporary file beside it in that folder, flushed, so a folder swapped or remade after it was opened is never written through, since the rename by the path reaches the temporary only while the path still names the folder opened; the file read once more and the act refused if it no longer holds the bytes read in step 3, which closes the window to the instant before the rename; the file's mode kept, and a file the act makes given the mode it was staged with (a move carries its source's, `Act.move`) or else the umask's; a symlink's target written, so the link stays a link; `os.replace`; the directory flushed. A file without write permission is refused (`not-writable`), as is one whose folder lets no file be made beside it, by the file's name.
   - The act's record lines are appended, each under its own log's lock; then `done` is appended to the journal, and the index (below) brought up to it.
   - An act of the person's puts what it wrote into their look (`_follow_look`; Keep, the undo, Discard and a tick do so themselves), so their own act is never listed back to them as a change to keep: a file the look held as it was before the act holds what it wrote, one with another change waiting gets the act's change merged in by lines and keeps its look where the two meet, and a new open text file goes in. A file agents are denied is left, since the look does not watch it (`looks.watching`). An agent's act changes no look. Whose act it is is decided as it is asked for and kept in its `begin` line as `by` (`identity.agents_act`): an act under a name that says it is an agent's is one; a write the viewer asks for, over the write API, a run it started or the home page's create, is the person's whatever shell started the server or the home; and an act a command makes is an agent's in a shell an agent runs. The look follows before `done` is written, so a crash in between leaves the act for recovery to finish, and recovery follows the look as the act's line says, never by the shell it runs in. A Keep of in-place changes, and the viewer's Accept that keeps them, put them into the look the same way: what the look holds once they are in is the act's `look` (`looked`), written in its follow-up and again by recovery (`pending.relook`), and their keep lines are the act's records, so an act that writes no file and only a look is journalled too, and a cut one writes neither the look's change nor its line. When recovery puts a person's act back instead, as it does once the person has written a file back to its before bytes, what the act put into the look comes out again, and each suggested edit whose `kept` record landed with it is opened again, with the annotation that Keep resolved, as the undo of a Keep does (`_unfollow`): the logs are append-only, so the record is answered, never taken out.
   - The follow-ups run, still under the lock.
8. **An act that changes no file** writes no journal line. Its record lines are still appended, since a Keep of an edit whose text stands already writes nothing and records it kept.

**Records an act writes.** An act may also write loom's own records of what it did. Adoption, a pull, `loom mv`, atomize, a flat copy, an import, a version restored to a file, a fork and a page open it inside `writes.staging`, and while the act stages them so:
- the history's step files, the review origins and the sync record are staged into the act as files, journalled with their before and after bytes like a person's file;
- the history's ledger lines are record lines, guarded by `at`: each lands only while the ledger holds the number of lines it was planned after, since a step's number counts the lines before it;
- a reader of those records (`load_history`, `review_origins.read`, `history.versions.read_version`) sees what the act has staged, so its later steps are numbered after its earlier ones;
- an act opened inside it, such as the Settings write a pull makes when the main document moves, joins it rather than committing apart;
- the scan the records are derived from is taken before any file is written, over the files as the act will leave them (`scan`'s `overlay`, in which None is a file the act removes).

So the person's files and the records that say what happened to them are one transaction. A guarded line refused at the commit, because another writer recorded a step meanwhile, puts the whole act back. The history's text store is written ahead, as every act's is, and holds only what was read. Keep, Discard, restore and the undo still record their versions directly, inside the act.

An exception raised inside the block writes nothing. An exception during the commit, after `begin` (the file changed at the last read, a full disk), puts the before bytes back into each file already replaced while it still holds what the act wrote, checked at the last instant as every write is, removes the temporary files, appends `aborted` with the reason, and is raised to the caller, which answers the person with it. A temporary file that cannot be removed just then, as while its folder is being swapped, leaves the act begun rather than aborted, so recovery clears it; the failure raised is still the act's own. A file the person saved in the instant since loom wrote it is theirs and stays; the act is then left begun rather than called aborted, so the next recovery says so, naming each file, and its edits are refused by Keep until it is settled ("Recovery").

## One lock

The lock is `.loom/local/writes.lock`, taken with `loom.locks.locked`: an operating-system lock on the file, exclusive across processes and across threads, reentrant within a thread, gone when its holder dies (so there is never anything to clear), and refused with a message after `locks.WAIT` (120 seconds) of waiting. The viewer's server, every `loom` command in a shell and the MCP server's subprocesses all name the same file, because it is in the quilt's own `.loom/local/`, wherever `[quilt] history` puts the history.

Locks are taken in one order, outer to inner: the server's `publication_lock` (one process's threads), then `writes.lock`, then the ledger's lock, the record logs' locks and the id lock. Nothing takes `writes.lock` for the first time while it holds an inner lock, so no two holders can wait on each other; a thread that holds it already may take it again under an inner lock, as a `put` does inside `cli._quilt.drawing_ids`, since it is reentrant. A command that draws an id settles what a crash left as it takes `writes.lock`, before the id lock, as an act does.

## The journal

`.loom/local/writes.jsonl` is append-only. An act that writes files appends:

- `begin`: `act` (a unique id), `kind` (`keep`, `undo`, `discard`, `restore`, `put-back`, `tick`, `settings`, `adopt`, `pull`, `mv`, `atomize`, `linearize`, `import`, `restore-to`, `fork`, `new`, `page`, `pdf-save`, `patch`, `id`, `deloom`, `agents`; `writes.KINDS` names each as a person reads it), `actor`, `when`, `files` (each path with the digests of its before and after bytes, null for a file that is absent before or after), `splices` (for each file, each change as `{edit, at, old, new}`: what replaced what, where, and for which suggested edit), `edits` (each suggested edit the act writes, as `<edit id>:<generation>`), `undid` on an undo (each Keep it takes out, named the same way, and never in `edits`), `folders` (the folders writing its new files will make, which putting it back takes away where it leaves them empty), and `records` (each record line it appends, with the log it goes to, and for a guarded line its `at`, the number of lines the log held before the act's first line for it);
- then `done`, or `aborted` with why.

**The journal is this machine's.** It records loom's writes to the files on this machine, and its offsets, its unsettled acts and its lock mean nothing against another machine's files. So the journal, its index and its lock are in `.loom/local/`, which `.loom/.gitignore` keeps on one machine (`loom/src/loom/gitignore.py`), wherever `[quilt] history` puts the history; the digests it names point into the history's `texts/` store, which is committed with the rest of the history. Were it committed, a co-author's pull would bring their unsettled acts to be settled against these files, offsets into a journal that differs here, and appends that conflict in git. What travels instead is the record: the `kept` line in the edits' log, written with the act, so on a second machine an edit kept on the first is no longer open and is never written again; and the before and after bytes in `texts/`, so a version restores anywhere. The undo of a Keep reads the journal, so it is offered on the machine that wrote the Keep ("Undo of a Keep" below). A temporary file a crash left beside a text in the history's `texts/` is in no ignored folder, since a write's temporary file sits beside its target so the rename stays on one disk; `writes.recover`, which `loom serve` runs as it starts, removes one once it is an hour old, which no store in flight is, and an act does not, so a quilt used only from the command line keeps them until a server starts on it.

`.loom/local/writes-index.json` is a cache of the journal, never a second record: the byte offset of the journal read so far, the acts begun and not yet settled, and `wrote`, which maps each `<edit>:<generation>` loom wrote to the offset of its act's `begin` line. A reader takes the index, reads only the journal past its offset, and folds what it finds. An index that is missing, unreadable or past the journal's end is rebuilt from the start. So an act reads what was appended since the last one, not the whole journal: with 10,000 lines in it, an act took 112 ms once, while the index was built, and 11 to 12 ms after. The index itself grows with the edits loom has written, and 5,000 of them read in about a millisecond.

A reader outside the lock (the list of what waits on the person) judges an unsettled act as recovery will: what it wrote counts as written only when every one of its files holds its after bytes.

## Act ids, and why a repeat writes nothing

Every act gets a unique id. Ids made from an act's content would name a later act like an earlier one whenever a state recurs (tick, untick, tick again), and the third would be silently skipped.

What stops a write being made twice is a record read under the lock. The Keep of a suggested edit is named by `<edit id>:<generation>`, the generation being how many times the edit has been opened again; the journal's `wrote` holds every such name loom wrote, and no act writes one twice. An edit loom wrote whose `kept` line is missing (an act a crash left after its rename) is recorded kept, never written again. Every other act is either a state (a box, a setting, a version, a put-back: doing it twice leaves the same bytes) or is refused on repeat because its item, read under the lock, no longer waits (a discarded change).

A request id, which would let a viewer that lost an answer send the request again and get the first answer back, is not built; it would go in `begin`.

## Recovery

Every act settles what a crash left unsettled first, under the lock, and says what it settled on stderr, as `cli._quilt.drawing_ids` does, except where its thread held the lock already and so said it as it took it; `loom serve` runs recovery once as it starts (`writes.recover`), which also removes the temporary texts a crash left over an hour ago.

**Nothing in a journal is taken on trust.** A quilt copied as a folder carries its journal, so one someone hands you can carry a journal written to do harm: a record line bound for a shell's startup file, or an act that looks cut short and names a file outside the quilt, which undoing would create from bytes the quilt's own store holds. Before recovery reads or writes anything for an act (`writes.untrusted`), every file it names must be a path in the quilt, in its normal form, that stays inside the quilt with every symlink followed; every digest must have a digest's shape; every record line must be one JSON object bound for one of loom's own three logs, which must themselves lie in `.loom/` or the history directory; the act must name a file or carry a look, since the one act the door journals that writes no file is one whose only write is the person's look and its records, as a Keep of in-place changes, which recovery finishes like any other; and a look it carries must be one recovery may write (`writes._look_untrusted`): the quilt's reviewer's, from a person's act, each file it takes in a file in the quilt the look watches that a `keep` line of the act names, its text one the store holds or none for a file that is not there, and each place or tick in a file the act writes. An act that fails any of these is left as it is and reported, and nothing is done for it, nothing taken into a look among it. A digest that does not have a digest's shape is never made into a path anywhere (`writes.fetch`, `records.snapshots.read_raw`), whoever sends it. A crash in an act that wrote through a symlink to a file outside the quilt is therefore left for the person, not settled.

**Who can write the journal**, and what a line someone else wrote reaches through recovery, is [a section of its own](#who-can-write-the-journal).

For each act begun and neither done nor aborted, and trusted:

- its temporary files are removed;
- if every file holds the act's after bytes and its guarded lines can still land where they were planned (the log holds exactly the lines before them and then a beginning of them), the act had written everything: whichever of its record lines are not already in their logs are appended (a line is compared whole, so no record needs a new field for this), `done` is appended, and for a Keep or an undo the words loom wrote go into the person's look as its follow-up would have put them (`begin`'s `look`, `pending.relook`, only the quilt's own reviewer's look), so they are not listed as the person's edit; the follow-up that carries annotations onto changed words is not done again, and those annotations anchor as any do;
- else, if every file holds either its before or its after bytes, the act was cut short between files or before the first, or another step took the place its guarded lines were planned for: when the store holds every text it needs, the before bytes are written back into each file that holds its after, each only while it still does, and `aborted` is appended once all are back, with any folder under `.loom/` or the history directory that the put-back left empty removed, so a step's folder never outlives its files; when it lacks one, nothing is put back, so nothing is put back blind and a document is never left made of files from two moments without a word;
- else someone changed a file since the crash, and recovery changes nothing.

An act is never put back over a later act: where an act begun after it names any of the same files, done since (the journal's index keeps them, `Journal.crossed`) or itself cut short and not yet settled (`Journal.crossing`), and one of them still holds the bytes the earlier act wrote, those bytes may be the later act's, and the earlier act is left and said, even when every file holds them. Where those files read as before the earlier act, as once the person has restored the version from before it, putting it back writes nothing over the later act, and it settles as any act does. Putting an act back also takes away the folders its `begin` line says it made, where it leaves them empty, in the person's tree as under `.loom/`.

**Recovery writes outside every dot-named place, loom's own apart.** On a journal line's word it writes, makes or removes a file only where the real file the path reaches lies inside the quilt, under no folder whose name begins with a dot, and is not itself so named; the real `.loom/` folder, a folder and never a link, is the one exception (`writes._place`). The real file is found with every link resolved, and `.loom/` by the file system's own identity, never by comparing names: `.LOOM/` where case is ignored is loom's, a link from an open place into `.loom/` reaches loom's place, and a link to `.claude/`, from an open place or from inside `.loom/`, is judged by `.claude/`. What is judged is what is written: the parts of the real path judged are opened one at a time from the quilt's root, never through a link and each checked again as it is reached, and the file is read, written beside, renamed in or removed through the last folder opened (`writes._folder_at`), so a folder swapped for a link between the judgment and the write refuses the write, which a test makes happen in process and from a racing thread. A hard link is no way in, since every write replaces the file by a rename, which leaves the file under its other name as it was. Nothing a line or the config says moves loom's own place. The history is written only where it lies inside the quilt, in the real `.loom/` under no further dot-named folder or under no dot-named folder at all (`writes._history_place`); a history anywhere else, set by the person or by a line put back over `config.toml`, outside the quilt among it, is written by recovery not at all. An act whose settling would write it (a person's act, whose follow-up keeps the look's texts in the history, an act with a look or a ledger line, or one with a file there) is then left and said, and stays until the person settles it as it stands (below): moving the history afterwards settles nothing, since a move writes `config.toml` and a Keep's ledger line names the history where it was. An agent's act on open files settles as before. The config is not refused for this, and no setting changes it. The apps keep what they hold their own shells out of in dot-named places (their settings, permissions, skills and commands, git's config and hooks, an editor's tasks), and the next app will too, so the rule names no app and no folder; a test checks that every file loom writes for an app, the root instruction files apart, falls under it. A folder an act made is taken away with it only under the same rule. Loom's own temporary files beside an act's file, `.<name>.<token>.loom-tmp`, are cleared once the act is finished or put back, wherever they lie in the quilt, a dot-named folder among it, through folders opened without following a link: a regular file of that name is loom's own litter, which no app reads, and a move into `.drafts/` cut short would otherwise leave one there. An act whose putting back would write, make or remove a file in a dot-named place is left and said, whatever else it names. It settles once each such file reads as before the act, which removing it does where the act made it, after which recovery puts the rest back at once, the person's own files among it; or once the next act of the same kind is done that writes each such file again or finds it already as it would write it and says so (`w.confirm`; `Journal.again`), when recovery says so and leaves every file as it is. An update of a mirrored folder needs the second: cut short after it wrote a `.latexmkrc`, it is left, and the next update finds the file as Overleaf holds it and stages no change for it, so without saying so it would never settle the first. A pull cut short, or put back, settles nothing, nor does an act of another kind. A forged line could settle such an act as well, and gains no more by it than an `aborted` line already gives it: the act is no longer said, and nothing is written. Loom writes an app's file only inside a person's act being carried out, each in a one-file act, which is finished or put back with nothing to write; so the import writes the permission files in acts of their own once its own act is done (`agents.write_denies`), and an import cut short is put back whole. One cut short between the two stands, its permission file lagging the deny list, which `loom lint` says (`loom:agent-permissions-stale`) and `loom ai init` mends; importing the paper again is refused, since an import never overwrites a document. An act whose files the person or a source chose in a dot-named place, a move into a dot-named folder, an import of a paper whose figure or bibliography is a dot-named file (an input is inlined, never copied), or a pull that changes a workspace's `.gitignore` or a file under its `.github/`, is left the same way when it is cut short with such a file written and another not; a test cuts such a pull at each of its renames, and doing what the words say lets the next recovery put the rest back.

Every writer of the history settles what a crash left before it writes a line from outside an act (`writes.settle_for_history`, from `append_entry` and `write_step`), as every act and `cli._quilt.drawing_ids` do, unless it holds the door's lock already or the ledger's, which comes after the door's: so `loom live`, a draft closed or reopened, Keep all's line and adoption's refresh never write a step after an act in flight. Each says what it settled on stderr, as an act and `drawing_ids` do.

An act recovery leaves (untrusted, a file changed since, a text the store lacks, a file it would write in a dot-named place, a history kept where recovery writes nothing, or a file that changed while it was being put back) stays begun, and `recover` says so in one line naming each file as the act left it, as before it, or neither; `loom serve` prints it as it starts, and says it again at every start while the act stays; and the same act is a problem in the person's file (`loom:write-left`, from `writes.left`, which judges an act as recovery does) on Problems and in `loom lint`, where a person who starts no command sees it. The problem says what the journal records, not who began it, since a journal can come with a copied folder, and what makes it go, as the act's verdict says it (`_judge`'s `settles`): where a file changed since, the act settles once each file reads exactly as before it or as it left it, which removing a file the act made does for that file, and putting back the version History kept just before the act does for one it changed, where it kept one; where the store lacks a text, only each file reading as the act left it settles it; where putting it back would write in a dot-named place, each such file reading as before the act settles it, and so does the next act of its kind that writes each such file; where its history is kept where recovery writes nothing, only the person's settling ends it; and an act whose history lines were written in part and followed by another's, or that a later act wrote over, stays until the person settles it. Its edits are refused by Keep until it is settled, since loom may have written them. Any of them the person may settle as it stands (below).

So an act happens once its last file is renamed into place and its guarded record lines have landed where they were planned: before that it is undone, or left and said, never half kept in silence. An act whose files are all written is still put back, at the commit or by recovery, when another step took the place its history lines were planned for and none of them had landed. One some of whose lines landed and were then followed by another step's is left and said (`_tangled`), never put back, since that would leave those lines naming folders it removed. Recovery settles loom's own unfinished act, and only where every file still holds exactly what that act read or wrote and no later act has written over it; where the person has been at a file since, it reports and changes nothing (P13).

## Settling as it stands

A write recovery leaves stays until the person settles it, and their control for that is one: **Settle as it stands**, on the problem in the viewer (`loom:write-left`, whose fix carries the act's id as data) or `loom doctor --settle ID` in a terminal of their own (`loom.settling`). Before it, the viewer shows what it will do, every file and every suggested edit, in its own words with no id, digest or command (`write-settle-preview`), and settles only on the person's confirmation, saying what was done in its own words too. It is the person's alone, refused to a declared agent and in a shell an agent runs.

- **Their files stay as they are.** Settling is one act through the door, of kind `settle` ("a settling"), which leaves each file of the act it settles as it stands (`w.confirm`) and names that act (`settles`). That act ends with the settling's `done`, as an `aborted` line would end it, and recovery finishes a settling cut short only while those files still read as the person settled on.
- **Edit by edit, as the files show.** For each suggested edit the act wrote or undid, its own splice is found again at its place in the file now (`splices_of`, `place_in`), and only a splice that carries the edit's own words as its record holds them, its new text and for a replacement its quote, decides anything. The edit's words there: kept. The words they replace there, and the edit's words nowhere in the file: open again, so Keep may write it, once. Neither, and neither its words nor the ones they replace anywhere in the file: closed, as no longer applying, with that said on its card. A line chooses its splice's place and the words beside it, so where the file as a whole disagrees with the place, the edit is left as it is. An edit loom cannot judge, or one already in that state, is left as it is. Nothing else the act would have recorded is written, and the person's look is not touched.
- **The version it began, if it began one.** Its history lines land where they still can and every file of the version holds what the act wrote, exactly as recovery's finish lands them, so the version is kept. An act that began none, a move say, has none of its history lines written, as none of its other records are. Where they can no longer land, the version it began and never recorded is removed, through folders opened from the quilt's root without following a link and only where its real path is its own (`w.remove_own`), its texts kept in the history's store as every removal's are; the preview says this version is not kept. So no stray step stops the next version, and a settling is never refused for its history.
- **A forged line gains nothing.** A `begin` naming an act to settle ends it, as a forged `aborted` line already does, and writes nothing; one naming an act the journal does not hold before it ends nothing. A forged left line's edits are judged by the text in the file and the edit log's own words, so it can neither keep nor close an edit whose words are not where it says.

## Who can write the journal

**Only Claude Code, with its sandbox turned on and its retry outside the sandbox turned off or left to the person to allow, holds an agent's shell out of everything recovery believes; for every other app, and for Claude Code set any other way, the places agents are denied are a request an agent's shell can ignore.**

Everything recovery believes lies where agents are held out: the journal and its index, the history's store and ledger, the store beside the journal for files only this machine reads, the look, the edit and annotation logs, and `config.toml`. Loom's commands deny each of them to every agent whatever the list says (`agents.always_denied`), and the permission file loom writes for Claude Code names each (`agents.claude_denies`); a test notes every file recovery opens, over each of its verdicts, and checks it against both. The act's own files recovery only compares with the digests its line names.

So where an app holds its shell to that deny, no journal line can be forged. Where a shell's writes are left to the person's permission, a shell that can write under `.loom/` can write the paper, the config and the records directly, and a forged line gives it nothing more. It can still do a great deal through recovery, as it could itself: a line that names two files, holding the bytes it claims as its after and its before, reads as an act cut short and is put back, writing any text the store holds into any file of the quilt outside a dot-named place, a paper in a place agents are denied and `config.toml` with its deny list emptied among them, or removing one, all recorded as a person's act put back; a line in the form of a person's finished write is finished, and its follow-up takes an agent's waiting change into the person's look (`_follow_look`), as a line carrying a Keep's look with its `keep` line does, and neither can be told from an honest one. What an app holds its own shell out of lies in dot-named places, by each app's documentation below, and recovery writes nothing there but in the real `.loom/` (above), whatever a line, a link or the history's setting says, so a line under `.loom/` is no way past an app's own protection. A link a shell plants inside `.loom/` or the history carries none of loom's records: the look, the logs, the history's texts and the journal are written through folders opened without following a link, in every command and in recovery alike, so such a link refuses the write ("Loom's own places", below). The few files Claude Code protects outside such places (`lefthook.yml`, `bunfig.toml`, `pyrightconfig.json` and two wrapper `.properties` files) it holds from its file tools and from a command it can read, not from a script; Claude Code's shell can forge a line only with a script, since its redirect into `.loom/` is refused, and the script writes those files as easily. A quilt copied from someone else carries whatever its sender put in it, the journal among it, and recovery there changes only files inside that quilt (`writes.untrusted`), nothing its sender could not have put in the copy directly.

**Where this stops.** A line under `.loom/` gives a shell no write, through recovery, into a dot-named place outside the real `.loom/`, nor outside the quilt, a link planted inside `.loom/` or the history among the ways it might try. The one thing recovery removes in such a place is a temporary file of loom's own name, which no app reads. What it still gives is the reach accepted above: the person's own files that are not dot-named, written or removed as a person's act put back, and the look. And the stated limit stands: an agent in a quilt can act with the person's authority, since recovery cannot tell a line written in full from one loom wrote.

Two things recovery believes lie outside the quilt. The reviewer's name, which decides whose look a line may write, comes from the person's loom config and, where that names no one, from git's `user.name`, which the quilt's own `.git/config` can set: no deny of loom's names that file, though Claude Code's sandbox, Codex's sandbox and Cursor's protect it and Gemini CLI's documentation does not say, and recovery never writes it, since it lies in a dot-named place. A history kept outside the quilt, as `[quilt] history` may name one, is named by no deny of loom's, since each is relative to the quilt; only a sandbox that confines writes to the project folder holds it, and recovery writes nothing in it (above).

What each app's own documentation says, read on 2026-11-24:

- **Claude Code** (code.claude.com/docs: permissions, sandboxing, permission modes, settings). Its `Edit` denies refuse its own file tools, and in a shell command it can read, a redirect's target and the files of a command it knows (`cat`, `sed`, `tee`); a script that opens a file itself is not refused. Its sandbox is off until the person turns it on, on macOS, Linux and WSL2; on, the `Edit` denies become operating-system write denies on every command and its children, and a command may be retried outside it, which is put to the person, judged by a classifier, or run without asking, as the permission mode decides, unless the retry is turned off; a sandbox that cannot start runs commands outside it unless told to fail. Its own settings files, skills and `.mcp.json` are protected paths: its file tools ask before writing them, refuse, or write them, as the permission mode decides, a redirect into them is checked, and its sandbox refuses them even where an allow names them.
- **Codex** (learn.chatgpt.com/docs, OpenAI's own; developers.openai.com sends there). The rules file loom writes matches command prefixes only and names no path, and a command it allows runs outside the sandbox. A path inside the project can be denied only by a permission profile in Codex's own config, which binds sandboxed commands; loom writes none. Its sandbox is the operating system's, on by default in a project under git (writes to the project) and read-only elsewhere, and keeps `.git`, `.codex` and `.agents` read-only. A project's `.codex/` is read only once the person trusts the project.
- **Gemini CLI** (geminicli.com). No path deny is documented, and a project's own policies are said not to work yet. Its sandbox is off by default and on in its yolo mode, and on macOS confines writes to the project folder by default. Whether it protects `.gemini/` is not stated: not verified.
- **Cursor** (cursor.com/docs). Its editor's agent has no path deny. Its terminal sandbox may read and write the whole project, and some paths are write-protected whatever its settings: `.cursor/*.json`, `.claude/*.json`, `.git/config`, `.git/hooks/`, `.vscode/` and `.cursorignore`. What its shell may write outside the sandbox is not stated: not verified.

## Bytes, line endings and encodings

The door keeps every byte it is not asked to change. A splice maps the scan's offsets onto the file's own text, so a file with Windows line endings keeps them, and the text put in takes the line ending most of the file's lines use. An adoption writes a merged document whole, and keeps the same: each line the merge leaves as it was keeps its own ending, and each line it writes takes the file's most common one (`writes.with_endings`).

A file that is not UTF-8 is never spliced: the scan reads such a file as Mac Roman, which accepts any byte and is wrong for the Latin-1 files people have, so loom has no reading in which to place an edit or encode an agent's Unicode. Writing would guess; refusing damages nothing. The list says so on the edit before the person presses Keep, and the door refuses at the write (`not-utf8`). Restore and put-back write stored bytes back whole, so a version of a Latin-1 file comes back exactly.

A version keeps each file's bytes as they were (`history.steps.stamp_document`), so restoring it gives the bytes back, not the scan's reading of them. So does a version of a file (`model.md`, "History"): a pull names, in a `file-version` line staged with it, the bytes of each file it writes over that held a change made here and that no version it stamped holds as it is, bytes the act's before keeps in the store, and `history.acts.restore_file` writes them back whole, text or not, in an act of kind `restore` that keeps the bytes it replaces as a version of the file first. The text store under versions, looks and the journal reads and writes bytes: a text stored with CRLF comes back with CRLF.

## Where an act may write

Every path an act names is relative to the quilt, normalised, never absolute and never through `..`; a file that does not exist yet must have its directory inside the quilt. Anything else is refused with `outside-quilt`, whatever named it: a request, a version's list of files, a record. A symlink the quilt already holds is written through to its target, but in `.loom/` or the history, where a record an act stages is written through no link ("Loom's own places").

**Open.** Writing through a symlink is right for the person's own arrangement, a macro file they share between papers, and wrong for a link that arrived in someone else's repository and points out of the quilt: Keep would write through it, and a dangling one would let restore or put-back create its target outside the quilt. Refusing every link whose target is outside would refuse the first case. Recovery already refuses both (above); whether a live act should, or should ask, is not decided. An act left on such a link is said by the link's name, with that the act may have written its target, never with a claim that nothing was touched (`writes.left`).

## Undo of a Keep

The person undoes the Keep of a suggested edit in one step (`change-undo`, `pending.unkeep`): the viewer's Undo after Keep. It is an act of its own, kind `undo`, one for the whole request, every decision made under the lock.

- **Its Keep, by record.** The edit must be kept (else `not-kept`). Its Keep is the act the journal's `wrote` names for `<id>:<generation>` (`pending.keep_of`): the Keep of its generation when that Keep wrote, and for an edit a restore recorded kept the last Keep that wrote it. That act's `begin` line holds the file's before and after digests and the edit's splice (`{edit, at, old, new}`, `at` in the text after). An edit with no such act is refused (`not-written`): loom wrote nothing of it on this machine, either because its words were in already when it was kept, so that Keep wrote nothing and opening it again with its words in would only offer them to be written a second time, or because it was kept on another machine, whose journal stays there.
- **Its record, checked.** A journal travels with a quilt copied as a folder, so the `begin` line must pass `untrusted`, as for recovery (a file reached through a link out of the quilt fails it), and its splices must explain the texts it names (`writes.splices_of`): each `new` stands at its `at` in the after text, each `old` at its place in the before text, and the after text with every splice of the file reversed is the before text. Otherwise the edit is refused (`not-written`) with the reason, and nothing is written.
- **Its place, established exactly.** An undo writes only at the place its Keep wrote, never at like words elsewhere (`writes.place_in`). Where the file holds the Keep's after bytes, the place is where the Keep wrote. Otherwise the words and `BESIDE` (32) characters either side, taken across that Keep's other splices so that a neighbour is never only a space, are the region, and a file's start or end inside it is part of it. Both texts are read as the scan reads them (CRLF and CR as LF). The region must stand exactly once in the Keep's after text and once in the file now: a region that stands twice cannot be told from its twin by any alignment, since two alike blocks the person swaps share even their end with the texts before the swap, so it is refused. It must then be carried over unchanged to its place (`writes._shift`): by arithmetic when it lies wholly in what the two texts share from their start or from their end, found in one pass; otherwise by comparing only their differing middle, by lines anchored on lines that stand once in both (`writes.paired`, near linear and bounded by `PAIRING` times their lines): the region lies in lines the diff pairs, in order, or its one occurrence in the file lies between the same paired lines as the Keep's place. That order is what the diff decides that a search would not: a passage copied elsewhere after the original was reworded holds the region once, out of order with the Keep's place, and is refused. Its edges must meet the file's edge in both texts where they met it in one. Past `MIDDLE` characters of differing middle, or the work bound, the file changed too much there to be sure, and the undo refuses and says so; nothing that does not refuse costs more than a few passes over the file. Nothing is searched for. Where the place is not established (the person changed words beside or inside them, typed at the file's edge beside them, copied or swapped the passage so that it stands twice, or loom has since undone another edit of the same Keep whose words were among the neighbours), the edit is refused (`changed-since`) and nothing of it is written; the person restores a version from History instead. An edit refused in one file is undone in none. Edits kept together are undone together, as the viewer undoes them; Keeps beside one another are undone in the reverse of the order they were kept, as the viewer's history does.
- **Whole where it can be.** When the file holds exactly one Keep's after bytes and every edit that Keep wrote into it is undone, its before bytes come back whole from the store. Otherwise each splice is reversed at its place, and every other byte is kept. The words put back are the Keep's own bytes where the file is still as the Keep left it; otherwise every line break in them takes the file's own ending at that place, that of the nearest line break before it or after it, as Keep's words take the file's.
- **Kept first.** A version of each of the person's documents made of a file it writes is stamped inside the act ("Before undoing a kept edit", `kept_for` `undo`), from a scan that reads as the files do, taken again once when one moved. A file that moves after the undo was planned refuses the whole act (`changed`), which then writes nothing. The door stores the bytes it replaces, as for every act.
- **Records, with the files.** The edit's `reopened` line, so its next Keep is a new generation and a new act; the `resolved` line with `undo` that opens again the annotation its Keep resolved, while that Keep's resolve is still the annotation's last word; and an `unapply` line in the ledger. The `begin` line names the Keeps it undoes in `undid`, never in `edits`, so `wrote` keeps saying only what loom wrote. Recovery finishes these with the act.
- **After it.** The words put back go into the person's look, as Keep's words did, so an undo is not listed as an edit in the file. The look is given the undo's own change without listing the person's changes: where it held the file as it was before the undo it holds the file now, and otherwise each stretch the undo wrote over is carried to its place in the look by the place rule (`writes.carry`); only where that place is not established is the change put in by listing (`absorb`). Annotations on the words taken out are carried onto the words put back (`records/carry.py`), and only where an annotation stands on the blocks, since carrying lists the person's changes. Once the files are written the undo is done, and its answer says so whatever these steps do: a failure of the look's shortcut falls back to the listing, and a step that still fails is said in the answer, as recovery says one ("Your Changes may list them as your edit").

The undo is offered on the machine that wrote the Keep, because the journal is that machine's (above). What travels is the `kept` record and the texts, so on another machine a version from History takes the words out. In the viewer it is the history's Undo (the toolbar, ⌘Z, and the bar over Review's Proposed edits) in the tab where the Keep was made; the tab keeps its Keep steps in session storage under the quilt the server says it serves (`GET /_api`'s `quilt`), so a reload keeps them and another quilt later served on the same port is never offered them: when the stream comes back and `GET /_api` names another quilt, the steps in memory go too. Each step names the quilt it was made in, and none is made before the server has said which it serves; the server refuses an undo that names another quilt or none (`other-quilt`), so a tab that followed its port to a copy undoes nothing there; loom says when one is pressed whether it can still be undone. A step it says never can (`not-kept`, `not-written`, `changed-since`, `other-quilt`, or `no-such-change` for a suggestion the quilt does not have) leaves the history. Once the tab is closed no control undoes that Keep; offering the undo from the kept edit itself would need the manifest to list the kept edits whose Keep this machine can still undo. Undoing a Discard of a suggested edit only opens it again (`change-discard` with `undo`), since a Discard wrote nothing; a kept edit is refused there (`kept`), since opening it would leave its words in the file for the next Keep to write again. Restore and put-back take their bytes from the same store.

**Undo of an adoption.** Taking in an agent's copy keeps the document as it was first, as a version (`adopt-finish`'s `landmark`), and its step names that version (`kept_as`). Restoring it is the adoption's undo: a restore like any other, one act through the door, the text it replaces kept as a version first, the file's bytes back exactly as the version kept them. Once that version is restored the adoption no longer bases the copy's comparison (`adopt._baseline`), so the changes it took wait in Review to be taken again. The viewer offers it where the copy was applied, an Undo beside Apply's answer for that page's life (`review/applied.ts`); its request names the quilt it was applied in (`quilt`) and is refused in any other, as the undo of a Keep is. Later, or from another page, the same version is restored from History.

**Records follow restore, put-back and Discard.** These three write a file's text whole or put words back, so they know the file's text before and after, and each updates the record of a suggested edit whose words it moves, at the place its Keep wrote them (`pending.follow_words`, journalled with the act's files). It looks at a Keep's place only when what it writes touches it: what the file's text before and after share at their start and end is found in one pass, and a Keep whose region, or the region of the words it replaced, stands once in either text outside what changed is passed over with no diff, as is any region that stands twice, which is never placed. A kept edit is opened again (`reopened`, `why: "restored"`) when the text after is the very bytes its Keep replaced, or when the Keep's words stand at their place in the text before, the words they replaced stand at their place in the text after, and the Keep's words stand nowhere in the text after at all. An edit open again whose last Keep wrote it is recorded kept (`kept`, `why: "restored"`) when the text after is the very bytes that Keep wrote, or when its words stand at their place in the text after and did not in the text before. Anything else leaves the record as it is, which errs toward an edit left kept with its words gone, harmless, and never toward an open edit whose words stand in the file, which a Keep could write a second time. The annotation a Keep resolved follows its edit either way, and an edit a restore recorded kept is undone like any other (its last Keep's place). Keep and the undo of a Keep do not update the records of other edits whose words they move: a Keep whose quote held an earlier kept edit's words leaves that edit kept with its words gone.

## What the rebuild may rely on

A write from the viewer answers once its act has committed, before the rebuild that publishes it, which follows under the server's `publication_lock`: held from the act through that rebuild, so no build comes between them, for every write but those that take their own lock (the library's intake, Overleaf, the reader's place), whose act runs outside it as before and which take it once the act is done, so the rebuild they name is still the next to begin; the answer names that build, and the page marks itself updating until it has published or failed (`docs/specs/write-api.md` §2). The rebuild may rely on the following.

- A process holding `writes.lock` sees no other process's act between its `begin` and its `done`: a scan taken under the lock sees each act whole or not at all.
- Recovery has run before any act, and any command that draws an id (`cli._quilt.drawing_ids`), holds the lock. An act still unsettled after it is one recovery could not settle, and is reported rather than hidden; the next step is numbered past every step folder there is, so it never shares a number with one such an act left (`History.next_step`).
- An act never takes `publication_lock`, never rebuilds and never runs TeX. It holds the lock for its reads, its plan, its versions, its writes, its records and its follow-ups, which scan the quilt at most twice (three times when Keep plans again). A scan inside an act's thread may take `writes.lock` again, since it is reentrant.
- An act's answer is final when it releases the lock, so the write API may answer then.
- The rebuild is to take `writes.lock` after `publication_lock` and before any inner lock, and hold it only to scan, never through TeX, so that a command in a shell waits at most `WAIT` for it (not built yet: within the server `publication_lock` keeps a build and the viewer's acts apart, and an act from another process may land while a build scans, which the watcher then builds again).

## Refusals

| code | means |
|---|---|
| `changed` | the file moved while the act was being decided, twice, or no longer reads as the caller read it (`put`'s `expect`, a page's `--base`); nothing was written |
| `not-utf8` | the file is not UTF-8, so loom does not write into it |
| `outside-quilt` | the path an act would write is outside the quilt |
| `not-a-file` | the path is not a regular file (a FIFO, a socket), which reading would block on |
| `exists` | a file the act would make is there already (`put`'s `new`, a move's target) |
| `gone` | a file the act would move is not there any more |
| `not-writable` | the file is read-only, or its folder lets no file be made beside it |
| `mirrored` | the real file a change reaches, links resolved, lies in the folder that mirrors an Overleaf project, compared by the file system's identity (`loom.overleaf.mirrored`); only an update from Overleaf, an act of kind `pull`, writes there. Judged at the commit, under the lock, before anything is journalled |

The write API answers each with status 409 (`docs/specs/write-api.md`). The undo of a Keep refuses one edit at a time, in its answer's `refused`, besides these: `not-kept`, `not-written` and `changed-since` ("Undo of a Keep").

## Where an edit goes

The door makes sure loom never writes an edit twice by its own hand: the journal says what it wrote. It cannot say what someone else wrote. Text the person typed in, or an agent wrote in place, while an edit was open leaves no record, and the only evidence is the text. So where a suggested edit goes is decided by rules about the text at its place, in `records/edits.py`, which the door then writes.

**The words beside its place.** An insertion is written against the words beside its place when it was suggested: a quote's selector records up to 32 characters either side of the quote (`suffix` after it, `prefix` before it), and an insertion at the head or foot of a body records the body's first or last 32 characters (`edge`, written by `loom suggest`; `''` for a body that was empty), or, for a key with no text of its own (a file whose text all belongs to the blocks in it, which Keep writes at the file's end or start), the file's own. An insertion is placed only while those words still stand right beside its place, compared with whitespace normalised (`place`); a neighbour recorded as only whitespace says the block's own text ended there, and holds while nothing but whitespace lies between the quote and that end; otherwise it is unplaced, said in the person's words, and Keep writes nothing. Text the person wrote in at the place since, and then touched, cannot be told from the edit by any reading of the text, and refusing is what keeps it from being written beside again. An edit that recorded no `edge` is placed as before.

A replacement whose new text holds its quote adds words either side of the quote, and is judged as an insertion on each side it adds to. A replacement of a whole body is placed only while the body reads as it did when it was suggested (`_same_body`): its words, whitespace normalised, against the body of the text the edit was written against, which `loom suggest` keeps in the history's `texts/`; a title or a label changed since leaves it placed, and where that text is not kept the whole block must be unchanged. The agent suggests it again against the body as it now reads.

**An edit's quote is found as written.** `loom suggest` finds the words an agent quotes as the page prints them when the source has them otherwise (`selectors.find_quote`), and records the source's own words (`make_selector`). From then on the quote is found only as written, whitespace compared normalised (`selectors.find_written`), by placement and by the taken test alike: read as the page prints it, `\emph{term}` stands wherever the plain word does, and an edit would be written over that word.

**Taken is judged at the place.** Whether an edit's text is in already (`taken_how`) is asked at the very point Keep would write it, found as `place` finds it, never anywhere in its block. An insertion, and a replacement whose new text holds its quote, read as taken only when the new text stands right at the place, in the file's text so that text which opened a section or landed past an `\end{…}` is seen, and when the words recorded beside the place stand right beyond the new text or are gone from beside the place. A phrase that already stood where an edit goes reads with its neighbour where it always was, and is not the edit. A `\uses{…}` taken in at a body's head is read as the head, the body starting after it with the words it started with. A long text the person took in and worked inside (twenty words or more, nine in ten still in order) reads as taken, `edited`, as before. Any other replacement has not been taken while its quote still stands whole in the block, whatever else stands there (a replacement that trims its quote leaves its new text standing inside the quote); once the quote is gone it is taken when its text stands in the block. A deletion is taken when its quote is gone.

**A key named by place.** A key like `FILE#proof:3` names whichever block is third in its file, so an edit on one records the line above its block (`near`) beside the hash of the text it was suggested on (`against`), and goes only where those say (`records/locate.py`, `follow`, below): to the one block of the file that still holds that text, or among several, the one under that line. Once the block's text has changed, an edit that quotes words goes to the block now at its place only while the line above it is the recorded one and no other block of the file holds the quoted words too (`place`); an edit on the body goes nowhere. It is never written into whatever block happens to hold the place.

`loom suggest` keeps two guards from before these rules, for what they still say:

| guard | what it refuses | why it stays |
|---|---|---|
| a quote that reaches the block's `\begin` or `\end`, or runs across a block inside it (`misplaced`) | the edit, at filing and at Keep | text beside a `\begin` or `\end` lands in the block around the one the edit names, and words in two pieces of the file cannot be replaced in one. It is no longer what stops a second write: an edit filed before the guard and written in by hand is read as taken where it stands |
| a block named by place that reads the same as another under the same line (`alike`) | the edit, at filing | nothing could tell the edit's block from the other afterwards (`follow`), so it would be unplaced from the moment it was filed |

A body is what lies inside an environment's head and before its `\end`, or below a section's heading and its labels (`body_span`), so a suggestion on a section's body never replaces its heading; a body replacement whose body runs across a block inside it, or holds a line that brings in another file (`\input`), is refused at filing and at Keep (`whole_body`), since those would go with it.

**Open.** Two insertions beside the same quote or body edge: once the first is kept, the second's recorded neighbour is gone and it is unplaced, rather than put in ahead of the first, out of the order they were suggested in; the agent suggests it again. Once its text has changed, an edit on a key named by place written before `context` was recorded has only the line above its block and its quote to go by ("Where a record goes"). An edit whose new text is the very words already beside its place (a body's own last words suggested at its foot) can read either way, since written and not written look alike there; nothing is lost whichever it reads as.


## Where a record goes

An annotation and a suggested edit name a key, and hold the hash of their block's own text when they were written (`against`), whose text the store keeps (`cli/review._version`), and what tells that block from others (`context`, `records/locate.context_of`):

- `before` and `after`: the nearest block on each side whose text stands once in its file, recognised by that text with labels left out, so a label moved onto or off it leaves it the same neighbour; with how many blocks lie between, or the distance to the file's edge;
- `kind`, what sort of block it is;
- `copies`: how many blocks of the documents held its very text;
- `twin`: whether another block of its file read at least 0.6 alike, word for word;
- `unread`, where no document read its file (a scratch file), else `documents`, those that did, where a note that comes to be on no block is listed;
- with a quote, `quote`: how many blocks of the person's files it stood in;
- for an insertion beside a quote, `beside`: the file's own words beside the place, which a block kept there since changes though the block's own text does not.

One rule says which block a record is on now, for both (`records/locate.py`, `follow`), and for a mention and an ask's block in the evidence log (`docs/specs/evidence.md` §3.7). **A record goes to a block other than the one at its own key only when nothing else could be meant; wherever two blocks could be, it is on none, and says so.** A record is only ever found on a block of a file some document reads: never in an agent's copy under `.loom/`, nor in a file no document reads, such as a backup beside the paper. `copies` and `quote` count the same blocks, so two machines record the same.

- **A stable key**, an id or a label, keeps the block that carries it: a record stays there, marked rewritten where that block no longer reads like it (`VERIFY` on detaches it instead; which is the author's to decide). The label moved, and the record follows its text, only where the record's text, labels aside, stands in one other block between the record's recorded neighbours on both sides (the block now carrying the label counted as the neighbour it was; once it no longer reads like the record, also left out, as for a block put in beside the old one and given the label), long enough to be someone's, whatever twin its context recorded; never to a copy standing elsewhere. While the block carrying the label still reads like the record, a copy of the record's text beside it is not the record's: a look-alike put in beside a block and given its label leaves the very file a copy put beside the block, the block then edited, leaves, and the record stays with the label. An id's proofs (`ID/proof`, `ID/proof/2`) are numbered by their place among its proofs: a proof at such a key that no longer holds the record's text and stands apart from its recorded neighbours is another one, and the record is on none. A record with no context stays on the key's block, as loom always read it. A key whose block is in a file no document reads now (an `\input` commented out to compile faster) is on no block, and is on its block again once a document reads the file; a record written while no document read the file (`unread`) stays on its block. The same holds for a key named by place.
- **A key a label gives** (`LABEL`, `LABEL/proof`; `docs/specs/source-contract.md` §2) is a stable key while the label keys its statement. When it keys none:
  - the label stays on its statement, which an id keys now: the record is that statement's, or its proof's at the same place;
  - **two statements carry the label**, a draft copied to a new file among them: a record about a place (a note, a comment, a suggested edit) is on the one in a document its context recorded it written in, and on none where that is not exactly one, but where that document holds the label twice, on the one its recorded neighbours stand by most, the record's very text breaking a tie; an acceptance, a claim about a text, holds for each of them that holds its very text in a file a document reads;
  - the label was renamed or deleted, or went to a statement with no proof where a proof's record was: the record goes with its text, as a key named by place does.
- **A statement's place** (`FILE#ENV:N`, its proofs' and its regions' keys) still names the statement once a label or an id keys it (`ScanResult.named`), and a record on it is read by the rules for a key named by place, below, against the block now at the place: a label added later to a statement that had none must not lose the notes already on it. An acceptance compares its dependencies by the keys they have now, so a dependency a label comes to key is neither removed nor added, and a child keyed by a label stands in its parent's text as its place (`NodeRec.marker`), so no hash moves.
- **A region** goes where the block it is in goes, and is on the same region there where one stands. One whose label was renamed or went is read in that block. A record with no `context` on a region whose block still holds its text is read there, as loom always read it.
- **A key named by place**, or a document's path once its file is gone:
  - **its own key's block** first: while it holds the record's text and no other block does now or did when it was written (a look-alike beside it would have had to be rewritten into its very words to take its key), or reads 0.6 alike with no neighbour standing elsewhere. That block is never left for another, however exact a copy elsewhere. Where the context recorded a twin or two copies, any block holding its very text, its own key's included, is taken only with no recorded neighbour against it, and with both beside it where the context recorded copies of its very text (with a copy right beside it one neighbour is no evidence) or one where it recorded only a look-alike (of several, the one with both beside it), and a block reading alike only with both beside it, no block holding its very text, and reading closer than any other by 0.1; with two or more holding it and no twin recorded, the one with both its neighbours beside it. A text with nothing of its own, its block being filled in where it stands between both its neighbours, stays there.
  - **otherwise, with `context`**, only a block nothing else could be: the one block holding its very text, where none other held it when it was written, else as above; where none holds it, or no block that does may be the record's by that rule, the one block reading 0.6 alike, ahead of every other by 0.1, and for a record whose block had a twin, or a block of another kind, only with both its neighbours beside it; its quote of four words or more, standing in one block alone where it stood in one alone. Neighbours never place a block by themselves: they choose among blocks that read like the record.
  - **a text with nothing of its own to recognise** (an empty proof, "Obvious."; fewer than four words of its own) goes only to the one block of its very text standing between both its recorded neighbours. A text of fewer than six words of its own is never followed by its words to a block a recorded neighbour says is not its own.
  - **without `context`** (one written before it was recorded): its own key's block while it holds its text, as loom always read it (an edit there while no other block of its file holds that text, or under its `near`), and an annotation's while it reads 0.6 alike and no other block of its file does; otherwise only its very text standing in one block alone, while no other block reads like it.
  - **an edit** is never taken at its place on its quote and the line above alone: Keep writes only where the record's block is known, and a replacement only where the two words nearest its quote on one side at least are those it was suggested among. An edit placed on no block is listed on none (`loom changes`, Review's cards).
- **Otherwise none.** An annotation is detached and names no block at all: the manifest lists it in `unplaced`, `target.key` empty, counted on no key and given no gone mark, so the block that took its key is never said to hold it. An edit is unplaced. Nothing looks for a quote outside the block a record is on, since a quote is unique in its block and not in its file (the study's `raw/check-labels.md`, KEY-5).

Every place that says where a note is asks the same rule: the manifest, `loom status` (which lists a note on no block apart), `loom ai annotations`, a message and `loom since`, a key's context, and the viewer, which lists a note on no block in no key's context but at the end of the Comments and Notes of one document, by its own words, and opens it there: the document that read its file when it was written (the manifest's `unplaced[].document`), else the default one; a link to it, and Review's To do, open that document at it, and To do never heads a group with a bare key. A note edited or answered is restated on the block it is on now, which its key may no longer name, never on the block that took that key.

An insertion whose `beside` no longer stands at its place is unplaced, so a second section suggested after the same quote is not written ahead of the first once the first is kept (decision 21's first choice).

**Open.** A record written before `context` was recorded cannot tell a block that moved and changed from one put in at its place, nor two blocks of the same text once one is put in above them: the first detaches, and of the second it keeps the one at its place, as loom always did. Nothing stamps `context` on such records; whether something should is the author's. A block rewritten where it stands past reading like the record detaches, since neighbours alone never place a record.

## Loom's own places

Loom writes its own files, in `.loom/` and the history, never through a link someone planted there: each folder on the way is opened from the quilt's root one part at a time without following a link, the file itself is opened with `O_NOFOLLOW`, and a file is renamed or removed by its name in the folder opened (`loom.own`). A folder or a file on the way that is a link, a dangling one among them, refuses the write (`Planted`, or `changed` for a record an act stages), and nothing is written, made or removed through it; a link removed is removed itself, never its target. A link above the quilt's root is the person's arrangement of their disk and is followed. The anchor is the quilt holding `.loom/`, so a history kept outside `.loom/` in the quilt is covered too; one kept outside the quilt is the person's, and only its file's own name is opened without following a link.

What this covers: the records (the annotation, edit, library, tag and evidence logs, the ledger, the types, the review queue and origins, the looks, the last-seen texts, the adoption decisions, the source sync), the history (its text store, its ledger and its steps, a step an act stages among them), the journal, its index and every lock, the agents' sessions, messages and `since`, `.loom/`'s format number and ignore file, and the library: its nodes and a batch's record, its documents and sources, the drops waiting, a delete's undo, the index, the thumbnails, the drawings and surveys with the run folders they compile in, emptied and removed, and the pages and boxes kept for a PDF; the agents' places (their scratch, the MCP server's run log, their copies and saved contexts, the agent layer's own records); the build (the site, its pictures, the snippets, closures and previews); and this machine's part of the quilt (the server's file and presence, the Overleaf mirror's part and loom's clone of it). In the machine's own place, anchored at loom's data folder: the server's write token, the formalization switch and what the last check found, the person's word for a work's compile, the home's list, address, jobs and logs, the drops waiting and the records of quilts being made, and the mirror's mark. `loom/tests/unit/test_planted_links.py` plants a link at each and checks a folder outside the quilt keeps its canary and gains nothing.

What still writes by path is listed, each with why, in `loom/tests/unit/test_one_door.py` (`BY_PATH`), which fails on any other raw write: the sweep and the server's presence, which already open their folders without following a link; temporary folders of loom's own; a quilt being made, before it holds a `.loom/`; the person's own config, where a link is their arrangement and is followed; the viewer's copies, whose start removes nothing through a link; and the machine's own TeX, which loom installs and assembles in its data folder by path, not yet moved. A file a third-party tool writes is out of reach of this: TeX's, `pdftocairo`'s, `pdftoppm`'s, SQLite's, git's and Lake's writes go by path, so a run's own folder is made by loom without a link and the tool writes in it, and a link where the library's index belongs is taken away before SQLite opens it.

Step 4 is placement, not the door ("Where an edit goes").

**Nothing else writes a person's file.** `tests/unit/test_one_door.py` reads every module of loom and fails on any call that writes, moves or removes a file outside `writes.py`, unless its module or function is listed as writing only loom's own places, each with why: the library's store, records under `.loom/`, the build's output, temporary trees, the machine's own places, the sync directory. A listing whose function or module no longer writes fails too. It reads the code's text, so it cannot see a subprocess, a write a library makes, a name built at run time or a mode or a time changed; its docstring lists these, and review reads for them. A command writes one file through `writes.put` (an act of its own, or part of one staging), a file the person named through `writes.save` (through the door inside the quilt, as an ordinary file outside it), and several as one act. A command that draws an id takes the door's lock before the id lock (`cli._quilt.drawing_ids`), in the order every holder takes them, and settles what a crash left first, so the history steps `loom stamp`, `draft`, `new`, `fork` and `history restore` record are never numbered against an act in flight. The door refuses a file that is not a regular file (a FIFO, a socket), which reading would block on (`not-a-file`).

**Open.** The follow-ups run under the lock, so Keep holds it through two scans. Moving them out (making what they compute part of the plan) would shorten the hold for the rebuild; it waits until the rebuild's lock is measured.
